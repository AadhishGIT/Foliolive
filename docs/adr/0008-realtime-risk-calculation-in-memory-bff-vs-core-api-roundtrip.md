# ADR 0008: Real-Time Risk Calculation & Limit Evaluation: In-Memory BFF vs. Core API Round-Trips

## Status

Accepted

## Context

In Foliolive, market data ticks are generated by the market simulator at a baseline rate of 5–10 ticks/sec across instruments, scaling up to $\ge 100$ updates/sec in stress-testing mode. On every market tick:

1. Portfolio market values and unrealized P&L must be marked to market.
2. Risk limits (e.g., Value at Risk 95%/99%, Max Drawdown, Sector/Single-Asset Concentration, Leverage) must be continuously re-evaluated.
3. If a limit threshold is breached, an `ALERT_FIRED` event must be emitted immediately to subscribed clients. When a breach normalizes, an alert clearance event must be broadcast.

We considered two architectural alternatives:

1. **Core API HTTP/gRPC Round-Trip on Every Tick**: BFF forwards every tick or batch to Spring Boot Core API via synchronous REST calls; Core API runs calculations against PostgreSQL and returns updated analytics and alerts.
2. **In-Memory BFF State & Valuation Engine with Core API Canonical Sync**: BFF caches portfolio positions, cost bases, and active risk limits in-memory. On every tick, the BFF runs incremental vector mark-to-market and parametric VaR limit evaluations in sub-millisecond time ($< 0.5$ ms). The canonical trade execution, historical simulation batch runs, audit log, and limit configurations remain authoritatively persisted in the Core API / PostgreSQL, syncing to BFF on initialization, trade events, and periodic reconciliations.

## Decision

We chose **Option 2: In-Memory BFF State & Valuation Engine with Canonical Core API Sync**.

### Rationale:

1. **High-Frequency Latency & Backpressure**: At 100 updates/sec (stress mode), making 100 network round-trips per second to the Core API introduces network serialization overhead, thread contention, and connection pool exhaustion, causing tick lag to exceed the 100ms batching window.
2. **Sub-Millisecond Computation**: Portfolio mark-to-market and parametric VaR updates require straightforward matrix/vector operations on held positions ($V = \sum q_i P_i$, $\text{PnL} = V - \text{Cost}$, $\text{VaR} = Z_\alpha \cdot \sigma_p \cdot V$). Running this in-memory in Node.js takes under 0.2 milliseconds for hundreds of positions.
3. **Resilience & Decoupling**: If the Core API undergoes database maintenance or brief network latency, the real-time market simulator and streaming dashboard continue operating seamlessly without dropped frames or visual stalls.
4. **Clean Boundary of Responsibilities**:
   - **Core API**: Authoritative record of truth, user identity & permissions, ACID trade execution, portfolio persistence, batch historical simulation VaR, and audit history.
   - **BFF**: High-throughput multiplexing, real-time tick streaming, sub-second P&L and limit breach detection, client batch coalescing, and WebSocket session management.

## Consequences

- **Positive**:
  - Sub-millisecond tick-to-broadcast latency across all connected WebSocket clients.
  - Core API and PostgreSQL are shielded from thousands of high-frequency read/write queries per minute.
  - Zero UI stutter during 100+ updates/sec stress tests.
- **Negative / Mitigations**:
  - Shared calculation formulas must stay aligned between Java (`RiskCalculationService`) and TypeScript (`realtime-engine.ts`). Mitigated through strict mathematical specification in `docs/risk-methodology.md` and automated cross-verification unit tests.
  - BFF holds working memory for active portfolio positions. Given that institutional portfolios typically hold tens to thousands of active positions, total working memory footprint is $< 15$ MB.
